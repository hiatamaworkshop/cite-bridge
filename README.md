# cite-bridge

English: [README.en.md](README.en.md)（正本はこの日本語の版で、英語の版は訳である）

論文の引用ごとに、原典の逐語と所在を錨として持たせ、その確認の状態を執筆のあいだ正しく保つ道具である。

## 何をする道具か

引用の誤りの多くは、実在する文献に、その文献が言っていないことを言わせるものである。この道具は、それを自動で見抜くのではなく、
次の三つを毎回行う。

1. 原稿の一文と原典の逐語を並べて読む場を作る（`review`）。
2. 人が確かめた結果を、本文と根拠の指紋で固定する（`approve`、`apply`）。
3. 本文か根拠が後で変わったら、要再確認として知らせる（`check`）。

機械が保証するのは、錨（逐語）が原典に実在することと、その所在までである。原典が主張を支えているかは、人の承認が保証する。
そのため「検証ツール」とは呼ばない。支持の判定を機械に任せない代わりに、人が見る材料を毎回同じ形で揃える。
承認者の一覧（設定の approvers）で model とした者の承認は、記録には残るが承認済に数えず、人の承認を待つ確認待ちとして残る。

道具が約束するのは、データの形（抜き書きと引用の欄、指紋、判断ファイルなど。SPEC.md §11.1）と、上の保証の文の二つである。コマンドと機能は約束しない。データの形を変えるときは版を上げ、移し方を書き、古い形を次の版まで読む（SPEC.md §11.2）。

## 構成

| 置くもの | 内容 |
|---|---|
| 抜き書き（文献ごとの md） | 原典の一箇所ごとの逐語・強さ・要約・言っていないこと。所在と照合は道具が導く |
| 引用（一ファイル） | 原稿の一箇所ごとの、抜き書きへの対応・理由・原文との差・承認 |
| 設定（bridge.toml） | パス、書誌の読み方、印の形、承認者。道具はこれ以外の論文固有の情報を持たない |

原稿の引用の直後に印（既定は〔c001〕）を置き、引用のファイルに同じ ID のブロックを書く。
引用は二種類ある。主張（原典の内容を述べる）は抜き書き・理由・原文との差・承認を持ち、人の承認を待つ。
指示（作品の名前や存在を挙げるだけ）は書誌の key だけを持ち、承認を求めない。引用の慣行どおり、参照した文献が書誌にあれば足りる。

## 最小の使い方

リポジトリの根で実行する。初めてなら、例の一式で一件の引用を最後まで通す `docs/getting-started.md` から始める。

1. 設定を置く。ひな形は SKILL.md の「設定」にある。書誌は keyline、BibTeX、CSL-JSON を読める。
2. 原本の PDF から抽出テキストを作る。`bridge.py extract`（頭書きつき。頭書きの無い古い抽出は `extract --header-only` で足す）。Web 資料は `bridge.py snapshot <key>`。
3. 抜き書きを書き、引用を書き、原稿に印を置く。印の無い出典は `bridge.py propose` で作業票にできる（`--key <key>` で key の候補に当たるものだけ、`--checkable` で機械で照合できる格のものだけに絞れる）。
4. `bridge.py derive` で導く欄（所在・照合・前後の文・要ヒューマンチェック）を書き、`bridge.py check` で整合を検査する。
5. `bridge.py review --html -o review.html` で承認の画面を作り、人が判断して判断ファイルを保存する。
6. `bridge.py apply <判断ファイル>` で書き込む。要ヒューマンチェックの抜き書きは、次の「原本での確認」で記録する。
7. 提出前は `bridge.py check --strict`、地点の記録は `bridge.py checkpoint`（承認者の一覧があるときは `--by <人>`）。

git の pre-commit に検査を置くには、同梱の `hooks/pre-commit` を使う（SKILL.md の「hook」）。

原稿が複数あるときや写しで試すときは、`bridge.py --citations <引用のファイル> <コマンド>` で引用のファイルを替える。設定で置き場を明示していない記録（`applied.json`・`candidates/`・`excluded.json`・`judgments.jsonl`）も、その引用のファイルと同じフォルダに置く（SPEC.md §9）。
替わるのはこれだけで、抜き書きとチェックポイントは元のものを使い、候補を受け入れたときの印は引用のファイルの `対象` が指す原稿に書く。写しで試すときは原稿も写して、写した引用のファイルの `対象` をそこへ向ける。

## AI に使わせるとき

使う側のリポジトリの、エージェントが読む指示ファイルには、次の短いブロックだけを写す。作法の文書（SKILL.md）は写さずに指す。
写すと、道具の版が進むたびに写しがずれるからである。置き先は AGENTS.md、CLAUDE.md、GEMINI.md など、使っているエージェントが読むものを使う人が選ぶ。
パスは既定の置き場所（`tools/cite-bridge/`）と設定（`bridge/bridge.toml`）のものなので、替えていれば読み替える。

```markdown
## 引用（cite-bridge）

- 読む文書: 引用・抜き書きを書く前に tools/cite-bridge/SKILL.md を読み、その作法に従う。ファイルの形は tools/cite-bridge/SPEC.md。
- 確かめるコマンド: 書いたら `python tools/cite-bridge/bridge.py derive` と `python tools/cite-bridge/bridge.py check` を走らせ、ERROR を残さない。
  提出前は `python tools/cite-bridge/bridge.py check --strict`。
- 正本: 引用の確認の状態は、設定 bridge/bridge.toml が指す抜き書きと引用のファイルにある。`@` で始まる行は道具が書くので手で直さない。
```

## 原本での確認（要ヒューマンチェック）

照合が近似一致か照合不能の抜き書き、OCR の抽出や OCR の文字の層の抜き書き、逐語の範囲に読めない字がある抜き書き、短い逐語（欧文 3 語以下・和文 10 字以下。偶然当たりやすく所在を保証しない）の抜き書きは、機械では逐語の実在を保証できない。
道具はそれに「要ヒューマンチェック」の印を付け、原本で確かめた記録が無ければ確認待ち（NOTE）として出す。確かめるのは人か、人が委ねた外部の AI である。

| コマンド | 内容 |
|---|---|
| `review --source-checks [--images DIR] [-o 出力.md]` | 原本での確認が残る抜き書きを一覧にする（md。頁の画像を添えられる） |
| `review --source-checks --json -o 依頼.json` | 外の AI へ渡す依頼（`cite-bridge-source-checks/1`）。答えは判断ファイルの `source_checks` に書く |
| `confirm <key#eN> --source --by <名前> [--result 一致\|違う] [--page "p.49 §4・3"] [--note …]` | 原本で確かめた記録を書く。違うときは --note に原本の字を書く |
| `apply <判断ファイル>` | 判断ファイルの `source_checks` を書く（逐語の指紋が今と合うものだけ） |

- 記録は、確認者・日付・結果（一致か違う）・頁と節・メモを持つ。確認者は承認者の一覧の名前で、model のときは抜き書きの書き手と違う者でなければ数えない（名前は全角と半角、大文字と小文字、前後の空白を無視して比べる）。
- 逐語を直すと記録は有効でなくなり、確かめ直しになる。道具は逐語を直さない。
- 0.2.0 までの自由文の記録は有効でない。確かめ直して記録し直す。

委ねる場合の決まり。

1. 要ヒューマンチェックの依頼は、人が外部の AI に委ねてよい。委ねるかを決めるのは人で、委ねる AI を承認者の一覧に model として載せるのも人である。
2. 委ねた AI は、`review --source-checks --json` の依頼を受け取り、その名前で判断ファイルを書く。人がそれを `apply` に渡す。
3. 書き手の AI（抜き書きを記入したモデル）は、自分の書いた抜き書きの原本での確認を記録できない。
4. 誰が確かめたかは、記録の確認者と、マニフェストの確認者の種類ごとの数に残る。最終の提出（`checkpoint --by`）は人が出す。
5. 道具は外部の AI を呼ばない。依頼の JSON を書き出し、判断ファイルを受け取るだけである。

## 分類器（任意の検査）

ブリッジが保存している欄の閉じた語彙（原文との差、強さ、など）を、外部の分類器（現在は Jev）に独立にもう一度付けさせ、記録と食い違えば印を立てる。
印を立てるだけで、承認の状態は変えない。確からしさは規則に使わない。設定しなければ何も変わらない。

| コマンド | 内容 |
|---|---|
| `classify` | 送る内容の見積り（要求の回数、問いの数、字数）だけを出す。何も送らない |
| `classify --send` | 判定が無い、または古い問いを、分類器へ送る。判定は台帳（`bridge/judgments.jsonl`、追記だけ）に残る |
| `classify --list [--all]` | 台帳の判定を、現在の記録と突き合わせて出す。何も送らない |

設定（bridge.toml）。鍵は書かず、環境変数 `JEV_API_KEY`（または `TYPESAFE_API_KEY`。同じ鍵の別名）で渡す。環境変数が無ければ、`bridge.toml` と同じ場所の `.env`（`JEV_API_KEY=...` の行）から読む。`.env` は、その場所の `.gitignore`（`bridge/.gitignore`）に入れ、コミットしない。git に無視されていない `.env` からは、鍵を読まない。

```toml
[classifier]
provider = "jev"          # 提供元。省けば分類器を使わない
model = "jev-latest"      # 省略可
max_chars = 6000          # 一回に渡す材料の字数の上限。超える件は送らない
# types = ["cite.diff"]   # 使う型を絞る（省くと、登録された型すべて）
```

外へ送るもの。原稿の文と、原典の逐語・前後の文（著作権のある PDF の抜粋を含む）が外部のサービスへ渡り、課金される。
`--send` を付けたときだけ送る。

### 既定の型（最小の三つ）

| 型 | 見る視点 | 突き合わせる記録 |
|---|---|---|
| `cite.diff` | 本文の文のうち、その出典を引く部分は、逐語に対して一致・言い換え・限定つき一般化・外挿のどれか | 引用の `原文との差`。記録より重い判定だけを印にする（`order`） |
| `cite.attribution` | 逐語は、著者の主張か、他者の紹介か、仮定か | 他者の紹介なら印 |
| `cite.not_said` | 抜き書きの「言っていないこと」の文は、原典に照らして正しいか（否定文を「書かれているか」と訊くと逆転するため） | 誤りなら印 |

分類器が確実に拾えるのは、目立つ言い過ぎ（範囲を広げる、断定にする、結論を足す）までである。限定や対象をわずかに変える細かい読み違いは、
実機の測定で、実際に見つかった誤りの多くを見逃した。細かい読み違いは人の確認で見る。印が無いことは、支持の確認の代わりにならない。

本文の強さを訊く型（`cite.strength`）は既定から外した。実機の測定で、承認済みの引用にも「強めている」と答え、区別ができなかった。
言い過ぎは `cite.diff` の 限定つき一般化 と 外挿 で拾う。使うときは、下の例のように `[[checks]]` で足す。

### 型を足す

検査の視点は `bridge.toml` の `[[checks]]` に足せる（同じ `type` は上書き）。材料と突き合わせる欄は、SPEC.md の欄名で指す
（`citation.<欄>`、`excerpt.<欄>`）。足すときの決まりは三つ。

- 閉じた選択肢にする。`labels` に「判定できない」を必ず含める。分類器に文を作らせない。
- 何と突き合わせるかを書く。記録の欄と比べるなら `compare`、無ければ印にするラベルを `flag_on` に書く。
- 文面か選択肢を変えたら、以前の判定は古くなる（型の文面の指紋が変わるため）。論理的に別の型にするときは `version` を上げる。

```toml
[[checks]]
type = "cite.strength"
version = 3
for = "citation"                     # citation（引用ごと）か excerpt（抜き書きごと）
question = "本文の文のうち、{about} を引いている部分は、原典の逐語と比べて、どの強さで述べているか。"
labels = ["同じ強さ", "強めている", "弱めている", "判定できない"]
flag_on = ["強めている"]
about = "citation.出典"              # 問いの {about} に入る欄
[checks.gloss]
"強めている" = "推測を断定にする、条件や限定を外す、範囲を広げる"
[checks.materials]
claim = "citation.sentence"
source = "excerpt.逐語"
```

登録された型の名前・版・文面の指紋は、`checkpoint` のマニフェストの `classifier` 欄に残る。
新しい型は、まず印を立てるだけで使い、人の承認との一致率を測ってから、承認の状態を下げる動作（`on_disagree`）を検討する。それはまだ実装していない。

### 文面を測る（classify --eval）

型の文面は、提供元ごとに効く言い方が違う。文面を変えるときは、測ってから採る。測定は台帳に書かない。

```
bridge.py classify --eval <測定の組.json> --variant <文面の案.toml> [--variant …] [--types 型 …] [--reps 2] [--split tune|holdout|all] [--verbose] [--send]
```

設定どおりの型（案の名前は「設定」）はいつも測る。新しい型だけを測るときは、その型を書いた案と `--types` を一緒に渡す
（設定に無い型は、設定の案では送らない）。

- 測定の組（`cite-bridge-eval/1`）は二種類の件を持つ。承認済みの引用（印が立たないのが正しい）と、その本文を人工的に壊した改変
  （限定を外す、推測を断定にする、結論を足す。`flag` に挙げた型で印が立つのが正しい）。正しい組だけでは検出の力が測れないので、壊した組を作る。
- 調整に使う組（tune）と確かめる組（holdout）に分けて数える。調整に使った組だけで測ると、当てはめすぎを見逃す。
  ほかの名前の分け（例 実際の誤りを集めた `real`）も、表に行として出る。
- 出力は、案と型と分けごとの「承認済みの誤った印」「改変の検出」「判定できない」「確率の一位と二位の差（曖昧さの目安）」「反復で同じ答えになった割合」。
  結果は測定の組の隣の `results/` に JSON で残る。
- 本文と原典の言語が違う組（日本語の本文が英語の原典を引くなど）は、言語の組（本文/原典、例 `ja/en`）ごとにも数える。
  言語は本文と逐語から道具が判別する（仮名か漢字を含めば ja、欧字だけなら en）。組が二つ以上あるときだけ、分けた表が出る。
  道具は訳さない。言語をまたぐ比較は提供元に任せる。言語の差を確かめるには、同じ内容を別の言語で書いた本文の件（`twin`）を組に置くと、
  元の件と印の立ち方が違った組が出る。改変に難しさ（`level`）を付けると、難しさごとにも数える。
- 作った改変は、作った者の見方に寄る。実際に見つかって直した誤りの当時の文を、`evidence` と `record` を指定して組に入れると、
  設計していない誤りで測れる（引用の印が無い文でもよい）。
- 文面の案は、`bridge.toml` の `[[checks]]` と同じ形の TOML で、同じ type の定義を上書きする。

材料の整え（既定）。本文の文から引用の印と出典の括弧を外し、どの出典を引く部分かは問いの側で名指す（`citation.出典`、筆頭著者と年）。
前後の文は 200 字で切る（抽出の残骸が一文に繋がって長くなるため）。

### 提供元を足す

アダプタは `classify(state, asks) -> verdicts` の一つだけである（`cite_bridge/classifier.py`）。
`Classifier` を継いだクラスを書き、`PROVIDERS` に一行足す。

## 実装の構成

入口は `bridge.py`（引数を受けて `cite_bridge/cli.py` へ渡すだけ）。実装は `cite_bridge/` に責務ごとに分けてある。

| モジュール | 内容 |
|---|---|
| config | 設定（bridge.toml）の読み込みと、設定で決まる状態（他のモジュールは `cfg.X` で読む）、欄名・値の定数 |
| source | 原典の正規化、照合、見出しと節の検出、前後の文 |
| bib | 書誌のアダプタ（keyline・BibTeX・CSL-JSON）と文献の格 |
| blocks | 抜き書きと引用の md の読み書き |
| derive | 導く欄（所在・照合・前後の文）を作る |
| manuscript | 原稿の印・文・指紋、網羅、承認の状態の計算 |
| check | 整合の検査（check）、網羅の一覧（coverage）、格の一覧（grade） |
| approve / apply | 承認・差し戻し・要約の確認・指摘の書き込みと、判断ファイルの適用 |
| propose | 印の無い出典の候補づくり |
| judge / classifier | 分類器による検査の核（型の登録、材料、台帳、記録との突き合わせ、要求と送信）と、提供元のアダプタ。judge は review を import しない |
| classify / evaluate | 分類器のコマンド（classify と --list）と、文面の測定（classify --eval） |
| review（templates/） | 確認の材料（md・JSON）と承認の HTML。HTML と JavaScript は templates/ に置く |
| fetch | PDF の抽出と Web 資料の写し |
| checkpoint | マニフェスト、道具の版、pre-commit、印の除去 |

## 文書

| 文書 | 内容 |
|---|---|
| SKILL.md | 使い方と運用の作法。コマンドの一覧、AI が守ること。普通の Markdown で、頭の name と description はエージェントの skill として置くときの入口 |
| SPEC.md | ファイル形式の正本。欄、指紋、承認の状態、判断ファイル、マニフェスト、設定、版の方針 |
| docs/getting-started.md | 始め方。例の一式（`examples/first-citation/`）で、準備の確認から一件の引用の承認と `check --strict` までを通す |

この README と上の三つには、同じ場所に英語の版（`README.en.md`、`SPEC.en.md`、`SKILL.en.md`、`docs/getting-started.en.md`）がある。正本は日本語の版である。
設計は `docs/design-0.3.0.md` にある（0.3.0 で足した仕組みの設計。日本語だけ）。

## 動かすのに要るもの

- Python 3.11 以上（標準ライブラリの `tomllib` を使う）。
- 標準ライブラリだけで動く。PDF の抽出（`extract`、PDF の URL の `snapshot`）にだけ `pymupdf` が要る。
  試験で確かめた版は `pymupdf` 1.28.2 と 2.0 である（どちらも全試験が通った）。`pymupdf` が無いときは、PDF を作る試験だけを飛ばす。
- 試験は `python -m unittest discover -s tests`。利用者のデータに依らず、一時フォルダに小さな一式を作って動かす。
  承認の HTML の JavaScript の試験には node を使う（無ければその試験だけ飛ばす）。

## 言語

- 文書の正本は日本語で、英語の版（`*.en.md`）は訳である。
- 出力の文（`check` や `review` が出す文、承認の HTML の画面の文）は、いまは日本語だけである。道具は翻訳の仕組みを持たない。
  別の言語にしたい人や言い方を替えたい人は、使う側で `cite_bridge/` の中の文を直す。出力の文は約束する範囲の外で（SPEC.md §11.1）、文の場所と文言は版が進むと変わりうる。
- 欄の名前と値は英語の別名でも書ける（`verbatim:`、`strength: observation` など。SPEC.md §10）。道具が書く導く欄（`@` の行）の名前は、設定の `[output] language = "en"` で英語になる。
- 英語の原稿では、設定の `sentence_end` を英語の文の終わりに替える（SKILL.md の「設定」）。

## 限界

- 照合できるのは、抽出テキストか Web の写しがある文献だけである。PDF も Web の写しも無い文献は、照合できない格になる。
  抽出が化ける PDF、OCR、JavaScript で描く頁は、近似一致か照合不能として人が頁の画像で確かめる。
- 印の無い出典（印を置いていない引用）は、この道具が確かめていない。`check` の「網羅」の行と `coverage` がその数と一覧を出す。
- 承認が形だけになっていても、道具は検出できない（頁の画像を開いたか等は記録しない）。防ぐのは事故で、悪意は防がない。
- 見出し（節）の検出は推定である。
