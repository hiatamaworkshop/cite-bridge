# 設計：公開物（発表した論文と一緒に出す、確かめ直せる一式）

2026-11-13 に書いた、公開用の書き出しの設計（[roadmap.md](roadmap.md) の C46）。方針と経緯は roadmap.md の「公開物」の段と C46 の節にある。
作業の単位は roadmap.md の項目（`C<n>`）で、この文書の中では番号を振らない。実装が済んだら、内容は SPEC.md へ移り、この文書は経緯として残る。

この文書は案である。「決めたこと」に挙げたもののほかは、設計者（Claude）が台帳のメモに沿って書いた案で、利用者が読んで決める。利用者が決める点は §12 にまとめた。

## 1. 決めたこと

2026-11-12（利用者。roadmap.md の「公開物」の段）:

1. 公開物は、検査に使った道具を自分で指す。必要なら道具の写しを同梱する。
2. 原本は同梱しない側に倒す。同梱するのは著作権の問題が無いと分かっているものだけ。
3. 公開するのは発表の後で、整理したものである。作業中のリポジトリをそのまま出さない。
4. 公開物は、書き出した一つの JSON を主にし、元のファイルを添える。読む側は JSON だけを読めば済む。
5. 読む側は cite-bridge でなくてよい。

2026-11-13（利用者。推奨の案のとおり）:

6. 逐語は既定で出す。文献ごと・抜き書きごとに外せる。外したものは、逐語の指紋と所在だけを出す（§5）。
7. JSON の鍵は英語（SPEC §10 の別名）にそろえる。値は今の日本語の語彙のまま持ち、英語との対応表を JSON に入れる（§4）。
8. 読む側が原本との照合をやり直すとき、SPEC が約束するのは完全な一致（空白だけを無視）だけである。それより緩い照合は実装ごとの手がかりとする（§8）。
9. 完全性を何で支えるかは、二つの案を比べてから決める（§9）。

## 2. 用語

- 公開物: 発表した論文と一緒に出す一式。公開用の JSON（一つ）と、添える元のファイルからなる。
- 公開用の JSON: 読む側がこれだけを読めば済む、書き出した一つのファイル。形式名は `cite-bridge-publication/1`（案）。
- 書く側: 原稿を書き、cite-bridge で記録を付け、公開物を出す者。
- 読む側: 公開物を受け取って確かめ直す者と、その道具。cite-bridge とは別の実装でよい（C47）。
- 公開物の ID: 公開用の JSON の中身から計算する、変わらない名前（§7）。

## 3. 公開物の中身と、出す条件

公開物のフォルダは次のものを持つ。

| ファイル | 内容 | 要るか |
|---|---|---|
| `publication.json` | 公開用の JSON（§4） | 要 |
| `source/` | 元のファイルの写し（引用のファイル、抜き書きのファイル、設定、マニフェスト） | 要（決めたこと 4） |
| `tool/` | 道具の写し | 任意（決めたこと 1） |
| `originals/` | 原本 | 任意。著作権の問題が無いと分かっているものだけ（決めたこと 2） |

出す条件（案）:

- マニフェスト（SPEC §8）がある地点からだけ書き出す。マニフェストは `check --strict` を通った地点にしか無いので、確認待ちの残る一式は公開物にならない。
- 書き出すときに、今のファイルの指紋がマニフェストの `files` と合うことを確かめる。合わなければ断る（マニフェストの後に変わった一式を、そのマニフェストの名前で出さない）。
- 書き出しは、作業中のファイルを変えない。公開物のフォルダだけを書く。

出さないもの（案）: 抽出テキストの全文、頁の画像、作業票・下書き・候補、判断ファイル、適用の記録、差し戻しの履歴（`差し戻しの理由` と差し戻し時の記録の欄）、
分類器の判定の台帳の中身（マニフェストと同じ集計だけを出す）、原稿そのもの（引用を含む文だけを出す。§4.3）。

出す範囲を選べるもの: 逐語（§5）、承認者と確認者の名前（§6）、自由文の欄のうち判断の中身（`承認の理由`、`指摘`）。

`source/` に元のファイルを添えるとき、逐語を外した文献の抜き書きのファイルは、そのままでは逐語を含む。外した文献のファイルは添えない（案）。添えないファイルは、JSON の `publication.files` に名前と指紋だけを残す。

## 4. 公開用の JSON の形（`cite-bridge-publication/1`）

中身・確かめた記録・公開の情報を分けて持つ（ナノパブリケーションから取り込む候補。C46 のメモ）。分ける理由は、ID（§7）に入るものと入らないものを形の上で分けるためである。

```json
{"format": "cite-bridge-publication/1",
 "id": "<公開物の ID。§7>",
 "spec": {"version": "<書き出した道具の SPEC の版>", "fingerprint": "sha1-8", "identity": "sha256-jcs"},
 "tool": {"name": "cite-bridge", "version": "…", "sha256": "…", "commit": "…", "dirty": false},
 "vocabulary": {"strength": {"観察": "observation", "…": "…"}, "diff": {…}, "kind": {…}, "evidence_kind": {…}, "result": {"一致": "match", "違う": "differs"}},
 "content": {"manuscript": {…}, "sources": […], "excerpts": […], "citations": […]},
 "records": {"approvals": […], "summary_checks": […], "source_checks": […], "decided_by": {…}, "coverage": {…}, "classifier": null},
 "publication": {…}}
```

- `spec`: 読む側が、どの定義で指紋と ID を計算し直すかを知るための欄。`fingerprint` は SPEC §4 の指紋の定義の名前、`identity` は §7 の ID の定義の名前である。定義を変えたら名前を変える。
- `tool`: マニフェストの `tool` をそのまま写す（どの版の検査で通ったか）。
- `vocabulary`: 値の語彙の、日本語と英語の対応。値は日本語のまま持つので（決めたこと 7）、日本語を読まない読み手と実装がここで引く。指紋の計算には使わない。
  対応は SPEC §10 の値の別名と同じである。原本での確認の結果（一致・違う）は §10 に別名が無いので、ここで足す（SPEC にも足す）。

### 4.1 `content.sources`（文献）

抜き書きか引用が使っている文献だけを並べる。

```json
{"key": "doe2020", "entry": "<書誌の一件の文>", "doi": "<DOI | null>", "url": "<URL | null>",
 "accessed": "<書誌の参照日 | null>", "retrieved": "<Web の写しの取得日 | null>",
 "grade": "<格>", "file": {"sha256": "<著者が使った PDF か写しの sha256 | null>", "pages": 12, "ocr_pages": "<頁の範囲 | null>"},
 "verbatim_published": true}
```

- 原本の指し方は、書誌の文、DOI、URL、取得日、著者が使ったファイルの指紋の五つである。読み手は、手に入れたファイルの sha256 が `file.sha256` と合えば、同じファイルだと分かる。
  合わないとき（別の版、出版社の版と著者の版）は、同じ版かは分からない。そのときに読み手ができるのは、逐語の照合のやり直し（§8）である。
- `doi` と `url` は書誌の文から取る。書誌のアダプタ（keyline・BibTeX・CSL-JSON）が持つ欄があればそれを使い、無ければ書誌の文から正規表現で拾う。拾えなければ null。
- `file` は抽出の頭書き（SPEC §2.4.1）と Web の写しの頭書きから取る。頭書きの無い抽出テキストでは null。
- `verbatim_published`: この文献の逐語を出したか（§5）。

### 4.2 `content.excerpts`（抜き書き）

引用が根拠にしている抜き書きだけを並べる（どの引用も根拠にしていない抜き書きは出さない。案）。

```json
{"id": "doe2020#e1", "verbatim": "<逐語 | null>", "verbatim_fingerprint": "<逐語の指紋>", "verbatim_sha256": "<§5>",
 "strength": "観察", "summary": "…", "not_said": "…", "secondary_source": "", "translation": "", "alternate_location": "",
 "evidence_kind": "文", "written_by": "<記入>", "summary_fingerprint": "<要約の指紋>",
 "derived": {"match": "一致", "location": "…", "section_kind": "結果", "human_check": ""}}
```

- 書く欄（SPEC §2.1）は、鍵を英語の別名にして、すべて持つ。任意の欄は、無ければ空の文字列にする（`evidence_kind` は `文`）。
- `derived` は、書く側の道具が出した導く欄である。書く側がそう出したという記録で、読む側は信じなくてよい（§8）。前後の文（前・含む文・後）は原本の文なので、逐語と同じ扱いにする（逐語を出すときだけ出す。案）。
- 指紋は、読む側が計算し直して比べるために持つ。

### 4.3 `content.citations`（引用）

```json
{"id": "c001", "kind": "主張", "sentence": "<印を外した文>", "sentence_fingerprint": "<本文の指紋>",
 "excerpts": ["doe2020#e1"], "source": "", "reason": "…", "interpretation": "", "human_reading": "", "human_reading_by": "",
 "diff": "言い換え", "not_quotes": "", "written_by": "<記入>", "evidence_fingerprint": "<根拠の指紋>",
 "section": "<原稿の節の見出し>"}
```

- `sentence` は、引用を含む文から印と HTML コメントを外したものである。読む側は、設定と正規表現なしで本文の指紋を確かめられる（C45 で決めたこと）。
- 指示の引用は `kind` が `指示` で、`source` に書誌の key を持ち、`excerpts` は空である。
- 原稿の全文は持たない。発表した論文そのものは、公開物の外にある（`content.manuscript` で指す）。

`content.manuscript` は `{"title", "reference": "<発表した論文の指し方。DOI か URL>", "file": {"path", "sha256"}}`。`reference` は書く側が設定に書く（§10）。

### 4.4 `records`（確かめた記録）

誰が、いつ、何を確かめたかを、中身と分けて持つ。

```json
{"approvals": [{"citation": "c001", "by": "<名前 | null>", "kind": "human", "family": null, "date": "2026-01-01",
                "note": "<承認の理由 | null>", "sentence_fingerprint": "…", "evidence_fingerprint": "…"}],
 "summary_checks": [{"excerpt": "doe2020#e1", "by": "…", "kind": "human", "family": null, "date": "…", "summary_fingerprint": "…"}],
 "source_checks": [{"excerpt": "doe2020#e1", "by": "…", "kind": "model", "family": "anthropic", "date": "…",
                    "result": "一致", "page": "…", "note": "…", "verbatim_fingerprint": "…"}],
 "decided_by": {…}, "coverage": {…}, "classifier": null}
```

- 並べるのは、数えた記録だけである（マニフェストの `decided_by` の `counted` に入るもの）。数えなかった記録は、`decided_by` の `uncounted` の数だけを出す。
- 各記録は、確かめたときの指紋を持つ。読む側は、中身の今の指紋と比べて、その記録が今の中身についてのものかを確かめられる。
- `kind` と `family` は、承認者の一覧の種類と系統である。一覧が無いときは `kind` を `unlisted` とする（マニフェストのキーと同じ語）。
- `decided_by`、`coverage`、`classifier` は、マニフェストの同じ名前の欄を写す。

### 4.5 `publication`（公開の情報）

```json
{"published_by": "<公開した者>", "published_at": "<UTC 時刻>", "license": "<ライセンスの名前か URL | null>",
 "checkpoint": "<もとにしたマニフェストの時刻>", "replaces": "<置き換える前の版の ID | null>",
 "people": {"<名前>": {"orcid": "<ORCID | null>"}},
 "files": {"<公開物のフォルダの中のパス>": {"sha256": "…", "included": true}}}
```

- `people` は、承認者と確認者に外の ID（ORCID など）を持たせる欄である。必須にしない（取り込む候補。C46 のメモ）。
- `files` は、添えたファイルと、添えなかったファイル（`included` が false。§3）の指紋である。`publication.json` 自身は入れない。

## 5. 逐語を出す範囲

決めたこと 6 の形である。

- 既定は出す。設定で、文献（`doe2020`）か抜き書き（`doe2020#e3`）を挙げて外す（§10）。
- 外した抜き書きは、`verbatim` を null にし、`verbatim_fingerprint`（SPEC §4 の逐語の指紋）と `verbatim_sha256` と `derived.location` を出す。前後の文は出さない。
- `verbatim_sha256` は、逐語から空白（SPEC §4 の 29 字）を除いた文字列の、UTF-8 の SHA-256 の全桁（16 進の小文字）である。逐語を出すときも出さないときも持つ。
  逐語の指紋は 32 ビットしか無く、別の文字列でも合いうる。読み手が、自分で原本から写した文字列が著者の逐語と同じかを確かめるには、全桁が要る。
- 要約と言っていないことは、書き手の文なので、逐語を外しても出す。訳（書き手の訳）も出す。

決めていないこと: 逐語を外した抜き書きでは、読み手は原本を持たなければ何も確かめられない。外した数を `records` か `publication` に数として出すか（案: `content.sources` の `verbatim_published` から数えられるので、足さない）。
法的な確認（どの文献の逐語を出してよいか）は、書く側が行う。道具は判断しない。

## 6. 承認者と確認者の名前

名前を出すかは、公開物ごとに設定で選ぶ（§10。案）。

- 出す: `by` に名前を書く。`publication.people` に外の ID を足せる。
- 出さない: `by` を null にし、`kind` と `family` だけを出す。人か model かと、model の系統は、名前を出さなくても残る（誰の判断を数えたかは、公開物の主な中身である）。

記入（`written_by`）は、書いた者と日付の自由文である。名前を出さないときは、種類と日付に置き換える（案: 承認者の一覧で引けた名前は `human` か `model:<系統>` に、引けない名前は `unlisted` にする）。

## 7. 公開物の ID と、外からの指し方

公開物は書き換えない（取り込む候補。C46 のメモ）。直すときは新しい公開物を出し、`publication.replaces` で前の ID を指す。取り下げも、取り下げたことを書いた新しい公開物で示す（形は決めていない。§12）。

ID の作り方（案）:

- `{"format", "spec", "content", "records"}` の四つの鍵だけを持つ JSON を、RFC 8785（JSON Canonicalization Scheme）で直列化し、その UTF-8 の列の SHA-256 の全桁（16 進の小文字）を取る。
  `id` は `sha256-<全桁>` と書く。
- RFC 8785 のうち、この形で効くのは三つである。鍵を整列する、空白を入れない、文字列は必要な字だけをエスケープして UTF-8 のまま書く。数は整数だけを使う（小数を持たない）。鍵は ASCII だけなので、整列の順は符号位置の順と同じである。
- `tool`、`vocabulary`、`publication` は ID に入れない。同じ中身と記録を、別の日に別の置き場所へ出しても、同じ ID になる。
  `tool` を入れないのは、道具の版を上げて同じ中身を書き出し直したときに ID を変えないためである（`spec` は入るので、指紋や ID の定義が変われば ID も変わる）。

外からの指し方（公開物どうしをつなぐための形。案）:

- 引用は `<公開物の ID>#<引用の ID>`、抜き書きは `<公開物の ID>#<key>#<抜き書きの ID>`。例 `sha256-ab…ef#doe2020#e1`。
- ID が中身から決まるので、指した先の中身が後で変わることは無い。指す側は、ID のほかに何も持たなくてよい。

他の公開物の記録に依る判断（P の公開物の抜き書きを、書評 R が自分の根拠として指す）は、この版では形を決めない（§12）。決めるのは指し方だけである。
元の著者が確かめたことは、引く側の著者が確かめたことではないので、数え方には `decided_by` に別の区分が要る。

## 8. 読む側が確かめ直せること

公開物だけで確かめ直せること（原本は要らない）:

1. 公開物の ID（§7）。
2. 本文の指紋、根拠の指紋、要約の指紋、逐語の指紋（SPEC §4）。逐語を外した抜き書きを根拠に持つ引用の根拠の指紋は、計算し直せない（逐語が要る）。書いてある値を読むだけになる。
3. 各記録（承認、要約の確認、原本での確認）が、今の中身の指紋についてのものであること。
4. 数えた判断の内訳（`decided_by`）が、並んだ記録と合うこと。

原本を手に入れて確かめ直せること:

5. 原本のファイルが、著者の使ったものと同じであること（`content.sources` の `file.sha256`）。
6. 逐語が原本にあること。SPEC が約束するのは完全な一致だけである（決めたこと 8）。定義: 逐語と、読み手が原本から得た文字列の両方から、空白（SPEC §4 の 29 字）を除く。逐語が、原本の文字列の部分文字列であれば一致である。
   読み手が原本から文字列をどう得るか（PDF の抽出、OCR）は決めない。抽出の仕方で字が変わるので、一致しないことは、逐語が原本に無いことを意味しない。
7. 逐語を外した抜き書きでは、読み手が原本から写した文字列の `verbatim_sha256` が合うこと。

確かめ直せないこと（公開物が保証しないこと）:

- 主張を原典が支えているか。これは承認した者の判断で、公開物はその判断があったことを記録するだけである（README の保証の文と同じ）。
- 承認者が本当にその人か（§9）。
- 書く側の `derived`（照合・所在・要ヒューマンチェック）が正しいか。読む側は 6 でやり直す。

## 9. 完全性を何で支えるか（二つの案）

支えたいことは二つある。(a) 公開物が、出した後に書き換えられていないこと。(b) 公開物を出したのが、名乗っている者であること。

(a) は、どちらの案でも ID（§7）と `publication.files` の SHA-256 で支える。読み手が ID を別の経路（論文の本文、DOI のページ）で知っていれば、受け取った公開物が同じものかを確かめられる。違いは (b) である。

| | 案 A: 外の仕組みに任せる | 案 B: 道具が署名する |
|---|---|---|
| (b) の支え | 置き場所の仕組み。DOI を出す保管庫（Zenodo など）のアカウント、署名つきの git のタグ、論文の本文に書いた ID | 公開する者の鍵で、道具が ID に署名する |
| 道具の依存 | 標準ライブラリだけ（SHA-256） | 標準ライブラリに公開鍵の署名が無い。外のライブラリ（cryptography など）か、外のコマンド（`ssh-keygen -Y sign`、`gpg`）に依る。CLAUDE.md の 3 に当たる |
| 読む側の実装 | SHA-256 だけ | 署名の検証が要る。読む側の道具（C47）も同じ依存を持つ |
| 鍵の管理 | 無い | 書く側が鍵を持ち続け、公開鍵を別の経路で配る。鍵を失うか漏らしたときの手順が要る |
| 置き場所が消えたとき | (b) の支えも消える。ID は残る | 署名は公開物と一緒に残る。ただし公開鍵が誰のものかは、やはり別の経路に依る |
| 論文の本文に ID を書く運用 | そのまま使える。本文は査読と出版社が固めるので、ID が著者のものであることを本文が支える | 同じ運用を足せる |

設計者の見立て: 案 A を勧める。理由は三つある。

- 公開物は論文と一緒に出るもので、論文の本文（または補足資料）に ID を書けば、(b) は出版の仕組みが支える。道具が別に鍵を持つ必要が薄い。
- 署名を入れても、公開鍵が誰のものかを確かめる経路は外に要る。問題が鍵の配布に移るだけである。
- 読む側の実装を小さく保てる（決めたこと 5。AI に要る機能だけを持つ別の実装でよい）。

案 A でも、書く側が望めば外のコマンドで署名を足せる。公開物の ID を書いたファイルに `ssh-keygen -Y sign` か `gpg --detach-sign` をかけ、署名のファイルを公開物に添える。
道具はこれを呼ばず、検証もしない。手順を文書に書くだけにする（`publication.files` に署名のファイルが入るので、添えたことは残る）。

## 10. 設定

bridge.toml に `[publication]` の表を足す（案）。書き出しのときだけ読む。

| 鍵 | 内容 | 既定 |
|---|---|---|
| reference | 発表した論文の指し方（DOI か URL） | 無し（無ければ null） |
| published_by | 公開する者の名前 | 無し（書き出しのときに要る） |
| license | ライセンスの名前か URL | 無し（null） |
| withhold_verbatim | 逐語を外す文献の key か、抜き書きの ID の並び | 空（すべて出す） |
| names | `show`（名前を出す）か `hide`（種類だけ） | `show` |
| notes | `show`（承認の理由と指摘を出す）か `hide` | `show` |
| replaces | 置き換える前の版の ID | 無し |
| people | `<名前> = { orcid = "…" }` | 空 |

## 11. 版の約束

- 公開物は止まったままで、読み手は後の版の道具で来る。SPEC §11.2 の「古い形は次の副版まで読む」は作業中のファイルの約束で、公開物には当たらない。
- 公開物の形式の定義は、SPEC から消さない。`cite-bridge-publication/1` の定義と、`spec.fingerprint`・`spec.identity` の名前が指す定義は、後の版の SPEC にも残す。
  形を変えるときは形式名の番号を上げ、前の番号の定義を残す。
- 永久に変えない欄は、`format`、`id`、`spec` の三つである（台帳の案は `format` と `tool`。`tool` は書く側の道具の記録で、読む側の動作を決めないので、ここでは外した）。
  読む側は、この三つを読めば、残りをどの定義で読むかが分かる。
- cite-bridge が後の版で古い番号の公開物を読むかは約束しない。読む側の道具（C47）が決める。

## 12. 利用者が決める点

読んで決めてほしい点を、設計者の案と一緒に挙げる。

1. 完全性（§9）。案 A（外の仕組みに任せる）か、案 B（道具が署名する）か。設計者の見立ては案 A。
2. 引用が根拠にしていない抜き書きを出すか（§4.2）。案は出さない。
3. 前後の文を逐語と同じ扱いにするか（§4.2）。案は、逐語を出すときだけ出す。
4. 名前を出さないときの `written_by` の置き換え（§6）。
5. 取り下げの形（§7）。案は無い。最初の実装の範囲から外し、要るときに決める。
6. 他の公開物の記録に依る判断の数え方（§7）。案は、この版では指し方だけを決め、数え方は別の項目にする。
7. `source/` に添えるファイルの範囲（§3）。案は、引用・抜き書き・設定・マニフェスト。逐語を外した文献の抜き書きのファイルは添えない。
8. 永久に変えない欄（§11）。案は `format`・`id`・`spec`。

## 13. ナノパブリケーションとの対応（参考）

主な形は公開用の JSON で、ナノパブリケーションへの書き出しは作らない（C46 のメモの案）。対応だけを示す。

| 公開用の JSON | ナノパブリケーション |
|---|---|
| 引用 1 件（`content.citations` の一件と、その根拠の抜き書き） | 主張のグラフ 1 つ |
| 抜き書きの逐語、所在 | 原本から抜き出した文（rdfs:comment）、頁と節 |
| `records` の承認・確認 | 来歴のグラフ（誰が、いつ、人か model か） |
| `publication` | 公開の情報のグラフ |
| 公開物の ID（SHA-256 の全桁） | Trusty URI（SHA-256 の全桁。直列化の規則は別） |
| `diff`（一致・言い換え・限定つき一般化・外挿） | CiTO の種類（includesQuotationFrom、citesAsEvidence など）に近いが、一対一ではない |

ナノパブリケーションに無く、公開用の JSON が持つもの: 逐語と言い換えの区別、原本との照合の記録、要ヒューマンチェック、誰の判断を数えたかの内訳（C46 のメモ）。
