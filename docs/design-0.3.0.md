## 3. 用語

- 要ヒューマンチェック: 機械の照合では、逐語が原本の字のとおりであることを保証できない抜き書きに付ける印。理由を値に持つ導く欄（§5.1）。
  確認するのは人で、人はそれを外部の AI に委ねてよい（§5.7）。印は確認の後も残り、確認の記録（原本での確認）で済んだかを判定する。
- 原本での確認: 要ヒューマンチェックの抜き書きを、原本（頁の画像、PDF、紙）で確かめた記録。書く欄で、形と有効の条件を §5.2 で決める。
- 確認者: 原本での確認・要約の確認・承認を記録する者。承認者の一覧に、種類 human（人）か model（AI）で載る。
- 書き手: 抜き書きや引用の「記入」の欄の先頭の語（名前）。
- 外部の AI への委譲: 人が、要ヒューマンチェックの依頼を外部の AI に渡し、その AI が承認者の一覧の名前（種類 model）で判断ファイルを書くこと。
- 抽出の頭書き: 道具が PDF から作る抽出テキストの先頭に置く `<!-- extract … -->`。元の PDF の指紋、頁の数、OCR の文字の層の頁を持つ（§4.1）。
- OCR の文字の層: PDF の頁のうち、頁を覆う画像の上に、見えない文字（OCR の結果）が載った頁。
- 抽出の診断: 抽出テキストの崩れのうち、機械で見分けられ、直し方の分かるもの（§4.4）。
- 孫引き: 原典の著者が、他の文献の主張や原則を紹介している逐語。その元の文献を記録する書く欄（§6）。
- 出典: 出典らしき括弧の中の一つの文献の参照。一つの括弧に出典が二つ以上ありうる（§8）。

## 4. 抽出の頭書きと抽出の診断（C1）

目的。PDF の抽出テキストに、どの PDF から作り、何頁で、どの頁が OCR の文字の層かを残す。これで抽出の崩れを機械で見分け、抽出テキストが元の PDF の指紋を持たない問題も解く。

### 4.1 抽出の頭書きの形

extract が書く抽出テキストは、次の頭書きで始める。頭書きの後に改行を一つ置き、その後に本文（今と同じく、頁ごとの `page.get_text()` を改ページ文字 `\f` で結んだもの）を書く。

```
<!-- extract
pdf: <設定の pdf_dir からの PDF のファイル名>
sha256: <PDF のバイト列の sha256（16進）>
pages: <PDF の頁の数>
ocr_pages: <OCR の文字の層と判定した頁。例 1-7、2,5-6。該当が無ければこの行を書かない>
extractor: pymupdf <pymupdf.__version__ の版>
extracted: <YYYY-MM-DD>
-->
```

- 鍵と値の行は `^(\w+): (.*)$` で読む（Web の写しの頭書きと同じ読み方）。
- `--header-only`（§4.3）で後から足した頭書きは、`extractor: 不明（頭書きは後から足した）` とし、`extracted:` の代わりに `annotated: <YYYY-MM-DD>` を書く。
- 頁の並びの文字列は、昇順の頁を連続でまとめ「a-b」、単独は「a」、区切りは「,」とする。読むときは数字と「-」の組をすべて拾う。

### 4.2 OCR の文字の層の判定（pymupdf、頁ごと）

頁ごとに次の二つを満たすとき、その頁を OCR の文字の層とする。

1. `page.get_texttrace()` の各 span の文字数（`len(span["chars"])`）を数え、描画の型 `span["type"] == 3`（見えない文字）の文字が全体の半分以上である。文字が無い頁は当たらない。
2. `page.get_image_info()` のどれかの画像の bbox と `page.rect` の重なりの面積が、頁の面積の8割以上である（`abs(pymupdf.Rect(bbox) & page.rect) / abs(page.rect) >= 0.8`）。

この規則を頁ごとに当てると、設計のときに調べた PDF のうち OCR の文字の層を持つ7件はどの頁も当たり、ほかの32件はどの頁も当たらなかった（2026-10-22 の走査。一部の頁だけが当たる PDF は無かった）。

### 4.3 extract のコマンド

- `extract [<key> ...] [--force]`: 今と同じく、書誌が PDF を指す文献の抽出テキストを作る。頭書きを付ける。既にあれば `--force` のときだけ作り直す。
  garbled() で抽出を使えないと分かったときは、今と同じく書かずに理由を出す。
- `extract [<key> ...] --header-only`（新規）: 既存の抽出テキストのうち、頭書きの無いものに、PDF から頭書きを作って先頭に足す。本文は一字も変えない
  （本文の前に頭書きと改行一つを足すだけ）。PDF が無いもの、既に頭書きがあるもの（extract・ocr・snapshot のどれでも）は飛ばし、その理由を一行で出す。
  `--force` と一緒には使えない（両方を渡したら断る）。

### 4.4 頭書きの読み方と、抽出の診断

source.py の Source は、先頭の `<!-- 種類` の種類で、snapshot（Web の写し）、extract（道具の抽出）、ocr（道具の外の OCR）を見分け、頭書きの鍵と値を持つ。

- 頭書きは照合の対象にしない。正規化（normalize）の前に、頭書きの部分を同じ長さの空白に置き換える（位置を保つ）。Web の写しの頭書き（URL や sha256）にも同じく効く。
- 頁の数（Source.pages()）は、本文（頭書きの後）を `\f` で分けた数とし、末尾の `\f` の後が空白だけなら、その空の頁を数えない。derive.py の printed_page が総頁に使う。
  これで、書誌の頁の範囲と総頁が合う文献は、所在が「p.N（PDF n頁目）」の形に変わりうる。derive で導く欄が更新されるだけで、承認と要約の確認の指紋には影響しない。
- Source に、頭書きの ocr_pages を頁の集合で返す関数を足す（extract の頭書きでないときは空の集合）。

文献の格（bib.py の grade_of）を次のように変える。

1. 抽出テキストが `<!-- ocr` で始まる: 今と同じく「PDF所持（OCR の抽出）」。
2. garbled() は、頭書きを除いた本文で判定する。当たれば今と同じく「PDF所持（<理由>）」で、抽出テキストを返さない。
3. extract の頭書きに ocr_pages の行がある: 「PDF所持（OCR の文字の層）」。抽出テキストは返す（照合と所在の導出に使う）。
4. それ以外は今と同じ。

check の grade の「機械で照合できるもの」は、今と同じく「PDF所持（抽出あり）」と「Web 写し（保存あり）」だけを数える。OCR の文字の層は数えない。

抽出の診断（bib.py に、key と書誌と Source から診断の文の並びを返す関数を置く）。直し方の分かるものだけを返す。Web の写しと `<!-- ocr` のテキストには診断しない。

1. 頭書きが無い: 書誌が指す PDF がそのフォルダにあり、抽出テキストに頭書きが無い。文は「頭書きが無い（extract --header-only で足す）」。
   PDF が無いときは診断しない（試験の一式と、PDF を持たない別の機械で、注意が出続けないように）。
2. 頁の区切りが合わない: 頭書きの pages が、Source.pages() とも、本文の改ページ文字 `\f` の数 + 1 とも違う。文は「頁の区切りが PDF と合わない（PDF N 頁、テキスト M 頁。extract <key> --force で作り直す）」（M は Source.pages() の値）。
   両方の数を認めるのは、最後の頁が空の PDF では、頭書きの pages（PDF の頁の数）と Source.pages()（末尾の空の頁を数えない）がずれ、どちらか一方だけで比べると extract --force でも直らない診断が残るため（利用者が 2026-10-22 に承認）。
3. PDF が替わった: PDF がそのフォルダにあり、その sha256 が頭書きの sha256 と違う。文は「抽出の後に PDF が替わった（extract <key> --force で作り直す）」。
4. 読めない字が多い: 本文の中の読めない字（正規表現 `[�-]|\(cid:\d+\)`、置換文字・私用領域・cid）が、本文の字数（空白を除く）1,000字あたり1を超える。
   文は「読めない字 N（置換文字・私用領域・cid）」。これは情報で、逐語の範囲にあるものは §5.1 で要ヒューマンチェックにする。

### 4.5 表示

- 抜き書きのファイルの頭の導く欄に、診断があるときだけ `@抽出の診断: <診断の文を「；」で結ぶ>` を書く（`@格`・`@抽出` の後）。英語の別名は extraction_diagnosis。
- check: 抜き書きのある文献で、診断 1〜3 があれば NOTE `<抜き書きのファイル>: 抽出の診断: <文>`。診断 4 は INFO。
- grade: 格ごとの一覧の後に、診断のある key を一行ずつ `<key>: <診断の文>` で出す。
- propose の作業票: key の候補ごとに、格と並べて診断の文を載せる（作業票の JSON の keys の各要素に `diagnosis` を足し、work.md にも出す）。

### 4.6 試験

pymupdf で試験用の PDF を作る（例: 一頁目は `page.insert_text` で普通の文字、二頁目は頁全体に画像を `page.insert_image(page.rect, pixmap=…)` で置き、
その上に `page.insert_text(…, render_mode=3)` で見えない文字を置く）。pymupdf の API は実装の時点で確かめる。

1. extract が頭書きを書き、pdf・sha256・pages が正しく、ocr_pages が「2」になる。
2. `--header-only` が、頭書きの無いテキストの本文を変えずに頭書きを足し、二度目は飛ばす。`--force` と一緒なら断る。
3. 頭書きの文字列（例えば URL や sha256 の一部）を逐語にした抜き書きは照合で一致しない。
4. 末尾が `\f` で終わる本文の頁の数を、空の頁を除いて数える。
5. 頭書きの pages が 3 で本文に `\f` が無いと、診断 2 が出て、check に NOTE が出る（`check` の終了コードは 0、`check --strict` は 1）。
6. 抽出の後に PDF を別の内容で上書きすると、診断 3 が出る。
7. ocr_pages のある頭書きの文献の格が「PDF所持（OCR の文字の層）」になり、grade の「機械で照合できるもの」に数えない。

## 5. 要ヒューマンチェックと原本での確認（C2: §5.1〜§5.4・§5.6・§5.8、C3: §5.5。§5.7 は C7）

目的。機械の照合では逐語の実在を保証できない抜き書きに印を付け、人（または人が委ねた外部の AI）が原本で確かめた記録を、確認者と指紋つきで残す。最終の提出は人が出す。

### 5.1 印（抜き書きの導く欄 `@要ヒューマンチェック`）

derive で、抜き書きのブロックごとに理由を集め、理由があるときだけ `@要ヒューマンチェック: <理由を「、」で結ぶ>` を書く（ブロックの導く欄の最後）。英語の別名は human_check。
理由は次のとおりで、当たるものをすべて挙げる。

| 条件 | 理由の文 |
|---|---|
| 照合が近似一致 | 照合が近似一致 |
| 照合不能（抽出テキストが無い） | 照合不能（<格>） |
| 不一致（逐語が抽出テキストに無い） | 照合で見つからない |
| 格が「PDF所持（OCR の抽出）」 | OCR の抽出 |
| 格が「PDF所持（OCR の文字の層）」で、逐語の頁が ocr_pages に入る | OCR の文字の層（PDF n頁目） |
| 格が「PDF所持（OCR の文字の層）」で、逐語が見つからない | OCR の文字の層 |
| 逐語に当たった範囲（抽出テキストの a から z）に読めない字（§4.4 の正規表現）がある | 逐語の範囲に読めない字 |

この欄は確認の記録に依らない。確かめた後も残り、「機械で保証できない抜き書きである」ことを示す。済んだかは §5.2 の記録で判定する。
頁の区切りが合わない（診断 2）は、道具で直すものなので、この欄の理由にしない。

### 5.2 原本での確認の記録の形

書く欄 `原本での確認` の値を、次の形に決める。

```
原本での確認: <確認者> <YYYY-MM-DD> <結果> [<頁と節>]（<メモ>）
```

- 結果は `一致`（原本に逐語のとおりある）か `違う`（原本と違う、または見つからない）。
- 頁と節は任意（例 `p.49 §4・3`）。Web の写しでは省いてよい。メモは任意で、全角の括弧で囲む。結果が `違う` のときはメモが要り、原本の字を書く。
- 記録の欄 `@原本での確認時の指紋` に、確かめたときの逐語の指紋を書く。逐語の指紋は、逐語から空白をすべて除いた文字列の SHA-1 の先頭8桁（16進）で、
  ほかの指紋（SPEC §4）と同じ作り方である。config.py の RECORD_FIELDS に足す（derive が消さない）。英語の別名は source_check_fingerprint。

有効な確認の条件。すべてを満たすときだけ、その抜き書きの要ヒューマンチェックは済んだとみなす。

1. 値が形に当たる。先頭の語が確認者、次が日付、次が結果。
2. 設定に承認者の一覧があれば、確認者が一覧にある。一覧が無ければ、確認者が「確認者不明」でない。
3. 確認者の種類が model なら、確認者が抜き書きの書き手と違う。書き手は「記入」の値の先頭の、空白と全角・半角の括弧の手前までの語である（例「Claude 2026-10-10（…）」の Claude）。
   種類が human なら、書き手と同じでもよい（人は最終の責任者で、一人で書く論文を想定する）。
4. `@原本での確認時の指紋` が、今の逐語の指紋と一致する。
5. 結果が `一致`。

結果が `違う` の記録は有効でない。逐語を直すのは書き手で、道具は直さない。逐語を直すと根拠の指紋が変わり、その抜き書きを根拠とする承認は要再確認に戻る（今の仕組みのまま）。
直した後に、もう一度原本で確かめて記録する。

0.2.0 までの自由文の記録（論文のデータでは kawahara2013 の4件。例「2026-10-10 p.49 §4・3 ユーザ（…）」）は、形にも指紋にも当たらないので有効でない。
道具は古い記録を書き換えない。確かめ直して、§5.4 の口で記録し直す。新しく記録するときにメモが無く、古い記録があれば、その文を `前の記録: <古い値>` としてメモに残す。

### 5.3 check

1. 要ヒューマンチェックの抜き書きで有効な確認が無ければ NOTE を出す。
   `<抜き書きのファイル>:<行> <key#eN>: 要ヒューマンチェック（<理由>）。<問題>（confirm --source か review --html で記録する）`
   問題の文は、欠けた条件に合わせて次のどれか: 原本での確認が無い／原本での確認の記録が今の形でない／確認者 '<名前>' が承認者の一覧に無い／
   書き手と同じモデル '<名前>' の確認は数えない／確かめた後に逐語が変わった（または指紋が無い）／原本と違うと報告された。逐語を直して確かめ直す。
2. 不一致は今と同じく ERROR（有効な確認があれば ERROR にしない）。
3. 今ある NOTE のうち、「<照合>。原本での確認が要る」（抜き書き）と「根拠 <ID> は <照合> で、原本での確認が無い」（引用）は、この規則に置き換える。
   引用の側は `根拠 <ID> は要ヒューマンチェック（<理由>）で、原本での確認が無い` とする（有効な確認が無いときだけ）。
4. INFO を一行足す。`要ヒューマンチェック: 印のある抜き書き N 件のうち、確認済 M（人 a、モデル b）、残り K（一覧は review --source-checks）`。
5. run_check の返り値に `source_checks: {"marked": N, "done": M, "by_kind": {"human": a, "model": b}, "pending": K}` を足す。

### 5.4 記録する口

1. コマンド `confirm <key#eN> --source --by <確認者> [--result 一致|違う] [--page <頁と節>] [--note <メモ>]`（`--source` が無ければ今の要約の確認）。
   - 既定の結果は 一致。違う のときは --note が要る（無ければ断る）。
   - --by を承認者の一覧に照らす（approve.py の approver_problem）。
   - 確認者の種類が model で、書き手と同じなら断る（§5.2 の条件3）。
   - 書いたら、approve.py の write_confirm と同じく derive して導く欄を並べ直す。欄を置き換えるときは `原本での確認` と `@原本での確認時の指紋` の行の両方を除いてから書く。
2. 判断ファイル（cite-bridge-decisions/1）に、任意の配列 `source_checks` を足す。
   ```json
   "source_checks": [{"id": "kawahara2013#e1", "fingerprint": "<逐語の指紋>", "result": "一致", "page": "p.49 §4・3", "note": ""}]
   ```
   apply は、fingerprint が今の逐語の指紋と合うものだけを、判断ファイルの by の名前で書く（合わなければ書かず、理由を出す）。
   配列を足すだけで、今ある判断ファイルはそのまま読めるので、形式の名前は `/1` のまま変えない。

### 5.5 確かめる材料（review）

1. review_data の根拠（ev_of）と、引用に使われていない抜き書き（excerpts_only）の各要素に、次を足す。
   `needs_check`（理由の文字列、無ければ空）、`check_ok`（有効な確認があるか）、`check_problem`（§5.3 の問題の文、有効なら空）、`check_record`（原本での確認の値）、
   `verbatim_fp`（逐語の指紋）。
2. 頁の画像を添える条件（今の `weak`）は、`needs_check` が空でないことに置き換える。
3. 引用の確認待ち（review.py の needs_review）に、根拠のどれかが要ヒューマンチェックで有効な確認が無いこと、を足す（承認済の引用でも確認待ちとして出る）。
4. excerpts_only に入れる条件に、要ヒューマンチェックで有効な確認が無いこと、を足す（今は要約が未確認のものだけ）。
5. md（既定の出力）: 根拠ごとに `- 要ヒューマンチェック: <理由>（確認済: <記録> / 未: <問題>）` の行を出し、判断のコマンドに
   `confirm <id> --source --by <者> --page "…"` を足す。
6. `review --source-checks [--images DIR] [--json] [-o FILE]`（新規）: 要ヒューマンチェックで有効な確認が無い抜き書きだけを、引用に使われているかに依らず並べる。
   md は人が読む一覧、JSON は外部の AI へ渡す依頼で、形は次のとおり。
   ```json
   {"format": "cite-bridge-source-checks/1", "manuscript": "<原稿>", "generated": "<作った時刻>",
    "instructions": "<道具が持つ定型の文（下記）>",
    "answer_example": {"format": "cite-bridge-decisions/1", "manuscript": "<原稿>", "generated": "<作った時刻>", "by": "<名前>",
                       "saved": "<ISO 時刻>", "decisions": [], "candidates": [], "confirms": [],
                       "source_checks": [{"id": "<id>", "fingerprint": "<fingerprint>", "result": "一致", "page": "", "note": ""}]},
    "items": [{"id": "kawahara2013#e1", "reasons": "OCR の文字の層（PDF 3頁目）", "verbatim": "…", "location": "…",
               "fingerprint": "<逐語の指紋>", "grade": "…", "page_image": "<--images の PNG のパス、無ければ null>",
               "record": "<今の原本での確認の値>", "problem": "<問題の文>", "written_by": "<記入>"}]}
   ```
   instructions の定型の文: 各件の逐語が、原本（頁の画像、無ければ原本の PDF か紙）に、そのとおりあるかを確かめる。字の違い（OCR の誤読、抜けた字、違う字）があれば
   結果を「違う」とし、メモに原本の字を書く。逐語が見つからないときも「違う」とし、メモにそう書く。頁と節が分かれば書く。答えは answer_example の形の判断ファイルに書き、
   by には承認者の一覧に model として載っている自分の名前を書く。抜き書きの書き手（written_by）と同じ名前では書けない。
7. 承認の HTML（review --html）。
   - 根拠のブロック（review.py の ev_html）に、要ヒューマンチェックの行（理由と、確認の状態）を出す。有効な確認が無ければ、その下に入力の行を置く。
     結果の選択（未・原本どおり・原本と違う。既定は未）、頁と節の入力、メモの入力。要素にはデータ属性 `data-scheck="<eid>"` を付ける。
     同じ抜き書きが複数のカードにあれば、ラジオの name はカードごとに分け、入力は JavaScript でそろえる（要約の確認の印と同じ扱い）。
   - 頁の画像は、今の weak の扱いと同じく details の中に置く（--html は既定で一時フォルダに頁の画像を作って埋め込む）。
   - 引用に使われていない抜き書きの節（orphans）に、要ヒューマンチェックの未確認のものも並べる。節の説明の文を、要約の確認か原本での確認が残るもの、に直す。
   - 頭の要約（HEAD）に「要ヒューマンチェック N 件」を足す。数の表示（count）に「原本での確認 N 件」を足す。
   - 埋め込むデータ（payload）に `vfp: {<eid>: <逐語の指紋>}`（要ヒューマンチェックで未確認のものだけ）を足す。
   - templates/review.js: collect で、結果が選ばれた抜き書きを `s.sources[eid] = {result, page, note, fingerprint}` に集める。localStorage への保存と復元に含め、
     復元のときに fingerprint が D.vfp と違えば戻さない。結果が「違う」でメモが無ければ、保存のときに断る（差し戻しの理由と同じ扱い）。
     buildOutput に `source_checks`（id、fingerprint、result、page、note）を足し、判断・候補・要約の確認・原本での確認のどれも無ければ null を返す。
     mergeStored は sources も合わせる。module.exports の関数は今のまま（試験が読む）。
   - HTML の説明の文（review.html の note）に一文足す。「要ヒューマンチェックは、機械の照合では原本の字を保証できない抜き書きである（OCR の文字の層、近似一致、照合不能、読めない字）。
     頁の画像か原本で逐語を確かめ、結果を選ぶ。外部の AI に委ねたときは、その AI が承認者の一覧の名前で判断ファイルを書く。」

### 5.6 マニフェストと最終の提出

1. マニフェスト（cite-bridge-manifest/1）に `source_checks`（§5.3 の 5 の集計）と `by`（checkpoint を出した者）を足す。
2. `checkpoint --by <者>`（新規の引数）。設定に承認者の一覧があるとき、--by は必須で、種類が human でなければ断る（最終の提出は人が出す）。一覧が無ければ任意で、無ければ by は null。

### 5.7 外部の AI への委譲の規則（README と SKILL.md に書く）

1. 要ヒューマンチェックの依頼は、人が外部の AI に委ねてよい。委ねるのは人の判断で、委ねる AI を承認者の一覧に model の種類で載せるのも人である。
2. 委ねた AI は、`review --source-checks --json` の依頼を受け取り、その名前で判断ファイルを書く。人がそれを apply に渡す。
3. 書き手の AI（抜き書きを記入したモデル）は、自分の書いた抜き書きの原本での確認を記録できない（§5.2 の条件3、§5.8）。
4. 誰が確かめたかは、記録の確認者と、マニフェストの by_kind に残る。最終の提出（checkpoint）は人が出す（§5.6）。
5. 道具は外部の AI を呼ばない。依頼の JSON を書き出し、判断ファイルを受け取るだけである。呼び出す仕組みは範囲の外（§12）。

### 5.8 書き手と確認者を分ける（model のとき）

委譲を許すので、書いたモデルが自分の書いたものを確かめることを、記録の種類によらず断る。確認者の種類が human のときは断らない。

1. 原本での確認: §5.2 の条件3、§5.4 の 1。
2. 要約の確認（approve.py の write_confirm）: 確認者の種類が model で、抜き書きの書き手と同じなら断る。check は、そうした記録を要約の確認として数えず、NOTE で知らせる。
3. 引用の承認（write_approval）と候補の受け入れ（propose.py の apply_candidate）: 承認者の種類が model で、引用（候補）の書き手と同じなら断る。
   check は、そうした承認を承認済として数えず、NOTE で知らせる（承認の状態の計算 approval_state は変えず、run_check の中で判定する）。

### 5.9 実装の場所

derive.py（理由）、check.py（有効な確認、NOTE、INFO、集計、§5.8 の判定）、manuscript.py（逐語の指紋、原本での確認の有効の判定、書き手の語の取り出し）、
approve.py（write_source_check、cmd_confirm の分岐、§5.8）、apply.py（source_checks）、propose.py（§5.8）、review.py（ev_of、needs_review、excerpts_only、md、--source-checks、HTML）、
templates/review.js と review.html、checkpoint.py（集計と --by）、cli.py（引数）、config.py（RECORD_FIELDS、FIELD_ALIASES）。

### 5.10 試験

1. OCR の文字の層の文献の抜き書きは、照合が完全一致でも要ヒューマンチェックの印が付き、check に NOTE が出る（check は 0、check --strict は 1、precommit は止めない）。
2. `confirm --source` で記録すると NOTE が消える。逐語を直すと NOTE が戻る（問題の文は「確かめた後に逐語が変わった」）。
3. 確認者が一覧に無い、形が古い（0.2.0 の自由文）、結果が 違う、のそれぞれで、NOTE の問題の文が出る。違う でメモが無い confirm は断る。
4. model の確認者は、自分が記入した抜き書きの原本での確認・要約の確認、自分が記入した引用の承認を記録できない。human は記録できる。
5. apply が source_checks を書き、指紋が合わないものは書かずに理由を出す。
6. `review --source-checks --json` の形（format、items の鍵、answer_example）。
7. tests/test_review_js.py: buildOutput に source_checks が入る。「違う」でメモの無い入力は断る関数があれば、その試験。fingerprint の違う保存済みの入力を戻さない。
8. checkpoint は、承認者の一覧があるとき --by の human を要る。model の名前と、--by 無しは断る。
9. 逐語の範囲に置換文字があると、印の理由に「逐語の範囲に読めない字」が入る。

## 6. 孫引き（C4）

目的。原典の著者が他の文献の主張を紹介している逐語（原典の中の孫引き）を、自由文の「言っていないこと」でなく、決まった欄で記録する。分類器の cite.attribution の印（他者の紹介）が、
記録があれば立たないようにする。孫引きの作法の最初の一歩である。

1. 抜き書きの書く欄 `孫引き`（任意）。値は、逐語が紹介している元の文献で、書誌の key か、著者と年の文字列（例 `西本（1996）`、`stepwrite2025`）。複数は「、」で区切る。
   英語の別名は secondary_source。
2. 要約の指紋（manuscript.py の summary_fingerprint）に、孫引きがあるときだけ、末尾に `\n孫引き\t<値（空白を除く）>` を足す。孫引きの無い抜き書きの指紋は変わらない。
   孫引きを書き足すと、その抜き書きの要約の確認は「確認し直す」に戻る（人がこの記録を確かめる）。
3. check。
   - 節の種類が 関連研究・参考文献 のときの INFO（原典の著者の主張でない可能性）は、孫引きがあれば出さない。
   - 主張の引用の根拠に孫引きのある抜き書きがあれば、INFO `<引用のファイル>:<行> <cid>: 根拠 <ID> は孫引き（<値>）。本文で元の文献に帰属させているか確かめる` を出す。
     値の中に書誌の key と一致する語があれば、同じ行の末尾に `元の文献は書誌にある（<key>）。直接引けるか確かめる` を足す。
4. 分類器（judge.py）。
   - 型の定義に任意の鍵 `cleared_by`（欄の指し方。例 `excerpt.孫引き`）を足す。flag_on のラベルが出ても、cleared_by の欄に値があれば、状態を `一致` とする（記録が同じことを言っている）。
     値が無ければ今と同じく 要確認。_validate で、cleared_by の指し方を materials と同じ規則で確かめる。compare と一緒には使えない（両方あれば断る）。
   - 既定の cite.attribution に `"cleared_by": "excerpt.孫引き"` を足す。spec_fp（文面の指紋）は question・labels・gloss だけを見るので、台帳の判定は古くならない。
   - values_at が抜き書きの 孫引き を読めるようにする（EXCERPT_FIELDS に `"孫引き": "secondary"` を足し、review_data の根拠の要素に `secondary` を足す）。
   - 状態は、表示のときに今の記録と突き合わせて決める（classify --list、review、§7 の数）。台帳の status は判定の時点のまま（SPEC §6.4 のとおり）。
5. review: 根拠のブロックに `孫引き: <値>` を出す（md と HTML）。
6. 試験。孫引きを書くと関連研究の INFO が消え、その抜き書きを根拠とする引用に孫引きの INFO が出る。要約の確認が「確認し直す」に戻る。cite.attribution の 他者の紹介 の判定
   （台帳を試験の中で書く）が、孫引きがあれば 一致、無ければ 要確認 になる（classify --list と review の両方）。

## 7. check の分類器の数（C5）

目的。check の「分類器: 判定 N 件のうち印 M 件」を、classify --list と同じ数にする。

1. 今の数え方の関数を judge.py に一つ置き、classify --list（classify.py の _list）、check、checkpoint のマニフェスト（judge.py の manifest_record）が同じものを使う。
   数えるのは、今の型・文面・材料で新しい判定（_list の fresh の判定と同じ）だけで、状態は今の記録と突き合わせた状態（§6 の cleared_by を含む）。古い判定は数えず、件数だけを出す。
   台帳にあっても単位（引用や抜き書き）が無くなった判定は、古い判定に数える。
2. 単位は review_data から作る（units_from_data）。check と checkpoint の中で review_data を呼ぶと run_check が二度走るので、review_data に run_check の結果を渡す引数
   （`checked=None`。渡されたらそれを使う）を足す。
3. import の循環に注意する。check.py はモジュールの頭で review.py を import できない（review.py が check.py を import している）。cmd_check の関数の中で import する。
   judge.py は review を import しない、という今の決まりは保つ（単位は呼ぶ側が作って渡す）。
4. check の出力の文は `分類器: 判定 N 件のうち印 M 件（今の記録との比較。一覧は classify --list）。古い判定 K 件は数えていない`。
5. 試験。台帳を試験の中で書き、材料（逐語）を変えた後に、check と classify --list の判定と印の数が一致する。

## 8. 出典ごとの網羅（C6）、propose の絞り込みと Web 資料の参照日（済）

### 8.1 出典ごとの網羅

1. 出典の分け方。COVER_RE に当たった括弧の中身を `;` と `；` で分ける。分けた一つずつの前後の空白を除き、全角の括弧で包んだ文字列が COVER_RE に全体一致するものだけを出典とする
   （例「（Dujmešić et al., 2018; §2.2）」の「§2.2」や、「（音声による…; Manaris & Harkreader, ASSETS 1998）」の前半の説明は出典でない）。出典が0か1の括弧は、今と同じく括弧で一件とする。2以上なら、出典ごとに一件とする。
2. 頁だけ・同書の括弧。設定 `[coverage] repeat_pattern` を足し、既定を
   `[（(](?:同書[^（）()\n]*|同上|同|ibid\.?[^（）()\n]*|pp?\.\s?\d[^（）()\n]*)[）)]` とする。当たる括弧も一件として数える（種類を repeat とする）。
   「（同一性と内容の分離）」には当たらない（「同」の直後は「書」か閉じ括弧に限る）。COVER_RE と repeat_pattern の両方に当たる括弧は COVER_RE の側で数える。
3. 一件の辞書（coverage_items の要素）に、`source`（出典の文字列。一件の括弧では括弧の中身）、`part`（括弧の中の出典の番号、0から。一件の括弧では None）、`kind`（cite か repeat）を足す。
4. item の ID。一件の括弧（repeat を含む）は今の式（文の指紋・括弧・n）のまま変えない（今ある候補と除外の記録を保つ）。出典ごとの件は
   `"q" + sha1(f"{fp}\t{paren}\t{nth}\t{part}")` の先頭7桁とする。
5. 印の判定（文ごと）。
   1. 文の中の印（MARK_RE）の ID を位置の順に並べる。印ごとに、引用のブロックから key の集合を作る（指示は 文献、主張は 抜き書き の key）。ブロックの無い印は key 不明とする。
   2. kind が cite の件ごとに、resolve_keys で key の候補と点数を出す。窓は、一件の括弧なら今の propose と同じく括弧の前の30字から括弧の終わりまで、出典ごとの件なら出典の文字列とする。
   3. key で結ぶ。印の key が件の候補にあれば、その組（点数、件、印、key）を辺とする。点数の高い順に、件がまだ印を持たず、（印、key）がまだ使われていなければ、件を印ありとし、
      （印、key）を使用済みに、印を使った印に足す。主張の引用の根拠が二つの文献にまたがれば、一つの印が二つの出典を受け持てる。
   4. 残りの件（key で結べなかった件と repeat の件）は、今の規則で判定する。括弧の直後に印があり、その印がまだ使われていなければ印ありとし、その印を使った印に足す
      （出典ごとの件では、同じ括弧の出典のうち前のものから一つだけがこの印を使える）。次に、使われていない印を、残りの件へ前から一つずつ割り当てる。
   5. 書誌と引用の key が渡されないときは 3 を飛ばす（今の判定と同じ結果になる）。
6. resolve_keys は propose.py から bib.py へ移し、propose.py はそれを import する（manuscript.py が propose.py を import すると循環するため）。
   coverage_items と coverage_of に、書誌と「印の ID から key の集合」を渡す任意の引数を足し、呼び出し元（check.py の run_check と cmd_coverage、propose.py の3箇所、review.py の1箇所）すべてで渡す。
   印から key の集合を作る関数を manuscript.py に置く（引用のブロックの並びを受け取る）。
7. 除外の記録（excluded.json）の要素に `part` を書けるようにする（無ければ None とみなす）。除外の照合は（文の指紋、括弧、n、part）で行う。propose.py の apply_candidate が除外を書くときに part も書く。
8. 表示。coverage の一覧は、出典ごとの件では `<出典>（括弧 <括弧> の出典 k/n）` と出す。check の網羅の INFO は
   `網羅: 原稿の出典らしきもの N（括弧 P）のうち、印のあるもの m、印の無いもの u` + 除外があれば `、引用でないと判断したもの x` + 今の括弧書きの注意、とする。
   マニフェストの coverage に `parens`（括弧の数）を足す。
9. 試験。二つの出典の括弧に印が一つで、その引用の key が二つ目の出典なら、一つ目だけが印の無いものになる。「§2.2」と説明の部分を出典に数えない。頁だけの括弧を数え、
   「（同一性と内容の分離）」を数えない。一件の括弧の item の ID が今と同じ。主張の引用の根拠が二つの文献なら、二つの出典を受け持つ。書誌を渡さないときは今と同じ判定になる。

### 8.2 propose の絞り込み（済 c75ec03。2 の repeat の除外は C6 で足す）

1. `propose --key <key>`（何度でも）: key の候補（resolve_keys の上位3件と --add-key）にこの key がある件だけ。
2. `propose --checkable`: key の第一候補の格が「PDF所持（抽出あり）」か「Web 写し（保存あり）」の件だけ。repeat の件は含めない。
3. 絞り込みは --limit で切る前に行う。そのため resolve_keys を、件を選ぶ前に計算する（今は --limit で切った後に計算している）。
4. 試験。--key で一件に絞れる。--checkable で、格が照合できない key の件が外れる。

### 8.3 Web 資料の参照日（済 c358d27）

1. 書誌のアダプタが、書誌の行から参照日を読み、各文献の辞書に `accessed`（YYYY-MM-DD か None）を足す。keyline は書誌の行の `参照\s*(\d{4}-\d{2}-\d{2})`
   （論文の書誌では「（参照 2026-07-30）」の形）。BibTeX は urldate、CSL-JSON は accessed の date-parts（年・月・日がそろうときだけ）。
2. check: 抜き書きのある文献で、格が「Web 写し（保存あり）」のとき、写しの頭書きの retrieved と書誌の参照日を比べる。違えば

## 13. ユーザが変えうる点（設計者が決めた細目）

1. 印の名前「要ヒューマンチェック」はユーザの語をそのまま使った。確認するのは人か、人が委ねた外部の AI である。
2. 人は自分が書いたものを自分で確かめてよい（§5.2 の条件3）。一人で書く論文を想定した。model だけを書き手と分ける。
3. checkpoint は、承認者の一覧があるとき人の --by を要る（§5.6）。最終の提出の主体は人、という判断を道具の規則にした。
4. 閾値。OCR の文字の層は、見えない文字が半分以上かつ頁の8割以上を覆う画像。読めない字の診断は1,000字あたり1を超えるとき。
5. 原本での確認の結果は「一致」と「違う」の二値とし、違うときの逐語の直しは書き手が行う（道具は直さない）。
